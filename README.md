# TrailCurrent Capstan

Firmware for the TrailCurrent **rotary touchscreen controller** — a round IPS
touch display inside a rotatable, pressable ring, wall-mounted in an RV or
trailer. It shows live state from the rig (climate, lights, energy, water,
air quality, levelling, doors) and controls what it can, talking to the
TrailCurrent Headwaters gateway over MQTT.

One source tree builds for **three different panels**. The board is chosen in
`menuconfig`; there are no per-board branches.

| Board | Resolution | Panel | Bus |
|---|---|---|---|
| Makerfabs MaTouch ESP32-S3 Rotary 2.1" | 480×480 | ST7701S | 16-bit RGB565 parallel |
| Elecrow CrowPanel 1.46" Rotary | 360×360 | JD9855 | 4-wire SPI |
| Elecrow CrowPanel 1.28" Rotary | 240×240 | GC9A01 | 4-wire SPI |

All three are ESP32-S3R8 — 8 MB octal PSRAM, 16 MB flash, native
USB-Serial/JTAG — verified by reading the silicon, not the product pages.

**Stack:** ESP-IDF ≥ 5.3 · LVGL 9.2.2 · EEZ Studio for the GUI.

## Quick start

```sh
. ~/esp/<version>/esp-idf/export.sh

idf.py set-target esp32s3
idf.py menuconfig          # Capstan -> Rotary display board
idf.py build
idf.py -p <port> flash monitor          # ls -l /dev/serial/by-id/
```

Before flashing a board for the first time, **back up its factory firmware** —
the vendors do not publish recoverable images. See
[DOCS/FactoryFirmware/README.md](DOCS/FactoryFirmware/README.md).

Full detail in [docs/build.md](docs/build.md).

## Repository layout

```

partitions.csv            16 MB: two 4 MB OTA slots + NVS + storage
sdkconfig.defaults        shared build config (never edit sdkconfig)

main/
  Kconfig.projbuild       board selection and tunables
  main.c                  boot, bring-up test screen
  actions.c  vars.c       hand-written EEZ glue  (NOT in main/ui/)
  ui/<res>/               GENERATED by EEZ Studio -- disposable

components/
  capstan_board/          the only board-aware code
  capstan_config/         NVS-backed settings
  capstan_wifi/           scan, join, credentials
  capstan_mqtt/           broker client
  capstan_model/          the data layer the UI observes

GUI/
  Capstan480.eez-project  one project per RESOLUTION -- not per board
  Capstan360.eez-project
  Capstan240.eez-project
  tmp/                    generator and patch scripts (gitignored)

docs/                     the documents linked above
DOCS/                     design handoff, vendor material, factory backups
```

### Why three EEZ Studio projects

**The split is by resolution, not by board.** An EEZ Studio project carries a
single `displayWidth`/`displayHeight` with no breakpoint concept, so one
project cannot serve three panel sizes — hence `Capstan480`, `Capstan360` and
`Capstan240`, named for their pixel size rather than for a product.

Nothing board-specific lives in them. A project knows nothing about which
controller, pin map or vendor is behind the glass; a fourth 360x360 board
would reuse `Capstan360` unchanged. All three are generated from one
description by `GUI/tmp/gen_eez_project.py`, so the palette, styles, fonts,
screen set and actions cannot drift apart.

**Only the selected board's export is compiled.** `main/CMakeLists.txt`
resolves the board symbol to exactly one of `main/ui/480`, `360` or `240`
and globs only that directory — no board ever links another panel's UI.

Full workflow in [docs/gui.md](docs/gui.md).

**The palette, fonts and icons are copied from Milepost, not designed here.**
Same 28 colour tokens with identical hex in both themes, the same four font
files byte-for-byte, and exactly the same 111-codepoint FontAwesome subset —
so two TrailCurrent panels mounted side by side are the same colours and the
same glyphs, not nearly. `GUI/tmp/palette.py --check` and
`GUI/tmp/fonts.py` diff against upstream, and the generator refuses to emit
anything if either has drifted.

Three structural rules hold this together:

- **`main/ui/` is disposable.** Delete the whole tree and re-export from EEZ
  Studio at any time. Nothing hand-written lives there — which is why
  `actions.c` and `vars.c` are in `main/`. See [docs/gui.md](docs/gui.md).
- **Board-specific code lives only in `components/capstan_board/`.** An
  `#ifdef CONFIG_CAPSTAN_BOARD_*` anywhere else means the abstraction is
  missing something. See [docs/architecture.md](docs/architecture.md).

## Status

**Hardware bring-up complete.** All three boards are validated end to end —
display, colour, orientation, touch with per-unit calibration, ring
rotation and ring press. The data path (Wi-Fi, MQTT, model) builds but is
untested. The product screens do not exist yet.

| Area | State |
|---|---|
| Board abstraction, Kconfig matrix | done |
| Pin maps, all three boards | done, every value sourced |
| ST7701S display bring-up (2.1") | **working on hardware** (needs a panel-specific init table) |
| GC9A01 display bring-up (1.28") | **working on hardware** |
| JD9855 display bring-up (1.46") | **working on hardware** (hand-written driver) |
| JD9855 driver | written; register table verified against upstream, untested |
| Touch (CST816 family) | **working on all three**, with per-unit calibration |
| Ring encoder (PCNT quadrature) | **working on all three**, direction + detents verified per board |
| Bring-up test screen | done, runs on hardware |
| RGB LED ring capability | config + runtime flag done; driver not written |
| NVS settings store | done, boots and loads defaults on hardware |
| Touch calibration engine | done (affine fit, NVS, versioned); screen is scaffolding |
| Wi-Fi scan / join / credentials | **verified on hardware** — scan, security picker, passphrase, connect, auto-rejoin at boot |
| MQTT client | **connects on hardware** (TLS 8883, self-signed); subscriptions confirmed |

| EEZ projects (palette, fonts, styles) | done, open cleanly in EEZ Studio |

Tracked debt:

- **The touch-calibration screen is currently hand-written in C**
  (`main/main.c`, behind the no-export guard). It is a user-visible GUI, so
  it must be authored in EEZ Studio with the project's colour tokens and
  fonts — a screen users see is a screen developers must be able to see in
  the canvas. The C version is a bring-up jig and gets **deleted**, not
  migrated, once the projects exist. The calibration *engine* stays in C;
  it is not UI. See [docs/gui.md](docs/gui.md).

Factory firmware for all three boards is backed up and checksummed under
`DOCS/FactoryFirmware/`; each image is identified from its own contents, not
from the port it came off.

Hard-won constraints worth not rediscovering:

- **Nothing may run on the system event task.** `capstan_wifi`'s state
  callback runs on `sys_evt`, whose stack is 2304 bytes, and starting a
  TLS MQTT client from there overflowed it and rebooted all three panels
  in a loop. Connection state is *polled* instead — from the 6 KB service
  task and the LVGL refresh timer. Same rule for the scan callback: it
  copies results and sets a flag, and the painting happens on the LVGL
  task.
- **LVGL's allocator is not the ESP heap by default.** The built-in pool
  is a fixed 64 KB and EEZ builds all 17 screens at boot, which needs
  ~60 KB. Overrun trips `LV_ASSERT_MALLOC`, whose default handler is an
  infinite loop — presenting as a watchdog timeout pointing at whatever
  allocation happened to be unlucky, never at memory.
  `CONFIG_LV_USE_CLIB_MALLOC=y` routes it to the ESP heap and PSRAM.
- **`__has_include` cannot detect a file that appears later.** It records
  no dependency on an absent path, so a unit compiled before the first
  EEZ export bakes in "no UI" forever. The generated UI's presence is
  decided in `main/CMakeLists.txt` and passed as `CAPSTAN_HAVE_UI`.
- **Energy is published on CAN frames, not on a timer.** Without live CAN
  traffic a value appears and is correctly expired 10 s later. That flicker
  is the staleness rule working, not a bug.

Known gaps, carried deliberately rather than guessed at:

- **The thermostat screen has no backing MQTT topic.** It does not exist
  anywhere in Headwaters. The GUI will be built and the backend stubbed until
  the CAN bus and MQTT design lands. No speculative schema has been invented.
- **Alerts are WebSocket-only** on the platform, so Capstan derives them
  on-device from the raw Picket and Spoor input bitmasks, mirroring Fireside.
- **Battery monitoring on the 1.46" is unwired.** The sense pin is known
  (GPIO18, via a 1K/1K divider) but it is on ADC2, which conflicts with the
  Wi-Fi radio. The sampling strategy is unresolved.

See [docs/mqtt.md](docs/mqtt.md) for the full gap list.
